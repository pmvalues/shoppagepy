05 Architecture Reality: TypeScript Kernel, Go Target

Core principle: The current live kernel is direct TypeScript (Next.js API route handlers), not NestJS, not a heavy framework. Go is a target extraction for high-RPS services, not a rewrite of working code. The TypeScript-to-Go migration is safer than a greenfield rewrite because frontend contracts, data models, and API shapes are already proven with 244 passing tests.

Current vs. Target Stack

Layer Current (Live) Target (Migration)
Frontend Next.js 16 App Router (TypeScript) Next.js 16 App Router (unchanged)
API / Backend Kernel Direct TypeScript (Next.js API routes, framework-light) Go (Chi/Echo) for high-RPS extraction
Search SQLite FTS5 (in-process, <1ms reads) Typesense 26 (typo-tolerant, faceted, geo-radius)
Database SQLite (inferred from FTS5 co-location) PostgreSQL 16 + pgvector (canonical write authority)
Cache / Sessions In-memory or file-based Redis 7 (sessions, rate limits, presence, AI cache)
CMS Payload 3.88 (packages installed, SQLite active) Payload over PostgreSQL
Scraping / AI Python 3 (Scrapy, Playwright, Gemini tooling) Python 3 (unchanged)
Payments Node.js (if any live integrations) Node.js (unchanged, SDK reality)

Why the TypeScript Kernel Makes Go Migration Easier

  1. No framework lock-in to break. NestJS has opinions about modules, providers, guards, interceptors, pipes. A direct TypeScript kernel has none of that. The Go equivalent is chi.NewRouter(), handler functions, and middleware. No conceptual translation layer needed.
  2. API contracts are thin and proven. The current backend is route handlers and data access functions with straightforward request/response shapes. Porting to Chi is moving handler logic and SQL from TypeScript to Go, not reverse-engineering a framework.
  3. Frontend contracts are validated. 244 passing tests mean the Next.js frontend already works against the current API. Go services must maintain backward compatibility, not invent new contracts.
  4. Data models are already validated. 36 merchants, live search, real mall catalogue — the schema is proven. The migration challenge is SQLite-to-Postgres, not schema design.
  5. Python and Node.js layers do not move. Scrapers, AI inference, and payment gateways stay in their optimal languages. Only the high-RPS API layer moves to Go.

08 RFQ / B2B Module: Strategic Recommendation

Verdict: Build it. Do not launch with it. The B2B quote/RFQ module is the strategic feature that turns Shoppage from "a better PriceCheck" into a commerce-native platform with a real moat. But it depends on three other contexts being live first: verified merchants, functional chat, and enriched product data.

Why RFQ Is Necessary

1. Least Contested, Fastest-Growing Segment

B2B/wholesale online in South Africa is growing at 10%+ CAGR with almost no dedicated platform. PriceCheck ($3.3M ARR, 17M shoppers) is purely B2C. The B2B ceiling does not exist yet.

2. Live Site Already Signals Intent

/search pages contain "Compare quotes and order via WhatsApp or direct counter dispatch." Buyers are primed. The merchant directory lists trade counters and wholesale hubs. The surface is there.

3. SA Commerce Reality Demands It

Most B2B quoting happens via WhatsApp, email with PDFs, spreadsheets, or phone calls. A structured RFQ workflow is a genuine 10x improvement: natural language requirement → AI parsing → merchant matching → line-item quote → approval → order.

4. Pemofy Makes It Possible

Shoppage does not need WMS, invoicing, or delivery management. Pemofy owns order execution and fulfillment. Shoppage owns the quoting layer. Clean architectural boundary.

Why RFQ Should Not Be Built First

  1. Highest dependency chain. RFQ requires verified merchant profiles (Geo), functional chat for quote delivery (Chat), and enriched product data for accurate requirement parsing (Product Intelligence). Building RFQ before Chat is like building checkout before a cart.
  2. Schema is designed but not implemented. The v10.0 spec includes full quotes, quote_lines, and conversations schemas. API contracts for generation and approval are specified. But no /quote path, no RFQ interface, and no merchant quote portal exist.
  3. B2B has higher trust requirements than B2C. A contractor requesting a quote for 500m of armoured cable with a 30-day account cannot tolerate a rough experience. RFQ requires merchant verification, buyer verification, quote validity enforcement, stock reservation, and audit trails.

Recommended Build Sequence

Priority Context Rationale
P0 Security + Auth Fixed in active monorepo. Deploy to production.
P1 Discovery Hardening Already live. Add product pages, categories, filters. Lowest risk, highest user value.
P2 Data Layer Wiring PostgreSQL, Typesense, Redis. Required by everything downstream.
P3 Chat Platform Required for quote delivery, negotiation, and approval.
P4 Product Intelligence Required for accurate requirement parsing and line-item generation.
P5 RFQ / B2B Build on top of verified merchants, chat, and enriched data.
P6 Markets & Communities Network effect layer. Launch after core commerce loop is proven.

The Counter-Argument: Skip RFQ, Focus on B2C Discovery

You could decide B2C discovery is large enough and RFQ is a distraction. The case: PriceCheck proves B2C product search works in SA; B2C has lower trust barriers, faster conversion cycles, simpler merchant onboarding; the live site already works for B2C.

Response: This is defensible for a Phase 1 launch, but it leaves Shoppage vulnerable. PriceCheck, Google Shopping, and Takealot all chase B2C discovery. B2B RFQ is the uncontested ground. If Shoppage wins B2B trade first, B2C discovery follows naturally (merchants bring retail catalogues). If Shoppage wins B2C first, B2B remains open for a competitor.

Bottom line: Launching without RFQ is acceptable. Never building it is not. It belongs in Weeks 17-20 of the roadmap, after Chat and Product Intelligence are operational. It is the strategic differentiator that makes Shoppage a platform rather than a search engine.
